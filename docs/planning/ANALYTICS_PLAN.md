# Analytics gap closure plan — solo / fresh Rust launch

Planning only; no code or deployment changes. Covers A1–A10 and deferred M1 in `docs/RUST_PARITY_AUDIT.md`. Assumptions supplied by the user: one engineer, fresh Rust installation first, release target 2026-12-20. Estimates below are focused engineer-days including targeted tests/review, not promised calendar durations. Preserve PostgreSQL as canonical analytics and keep warehouse delivery asynchronous.

> 🧠 **From Hindsight memory (Component map)** — PostgreSQL is the canonical analytics store; warehouses receive immutable durable event streams. The plan uses this existing choice to avoid a second identity-consistency subsystem for the initial release.

## Recommended scope decisions to write into the plan

1. All customer-facing analytics, including the basic `/projects/{id}/analytics` endpoint, must use canonical PG identities and counts. Warehouse raw event exports retain the original immutable visitor ID. Warehouse-direct, merge-aware ad-hoc SQL is a separate optional extension; do not imply raw `COUNT(DISTINCT visitor_id)` is canonical after merges.
2. GeoIP is server-derived country/city, with trusted-proxy client IP selection. No new client-supplied country override by default; preserve opaque client attributes under a noncanonical namespace if compatibility requires retaining them. UA OS/version and timezone are captured from the originating device/context. Explicit native `screen_name` is resolved with saved aliases/fallbacks matching retained behavior.
3. Freeze enrichment at first accepted ingestion. Replaying an event UUID or the stored outbox must reuse its original enriched snapshot, even after aliases, profile, UA parser or MMDB version change. Do not retroactively rewrite older events as a background side effect.
4. Restore range-sensitive usage exports (daily + partial-month uniques + zero-fill), separate from the monthly billing snapshot export. Because Rust is fresh, the first release needs no Rails data conversion or archive backfill. Native backup/restore remains mandatory.

## AN1–AN2 design: one frozen enrichment snapshot

- Extract a native enrichment service invoked by all `persist_events` entry points, including SDK ingestion, public-link generated events and imports of native fixtures. Existing `persist_events` is the common point; use a typed accepted-event structure rather than modifying read endpoints independently.
- Order: validate input → deduplicate/lock event UUID → resolve canonical visitor and capture correct originating device/request context → snapshot user attributes + trusted link attribution → resolve screen label and UA/GeoIP/device fields → write event and exact outbox payload atomically. Duplicate IDs return the accepted result without recomputing derived fields.
- Resolve screen as the Rails reference does: event property → visitor screen attribute → project alias; then alias of event name; then event name for CUSTOM/SCREEN_VIEW. Freeze the result. Test trimming, absent alias, overwritten alias, empty/missing fields and a later alias update.
- Parse OS/version from stored/trusted UA and preserve timezone/language/model/build as event-time context. Do not associate an event from device A with whichever other device happened to update most recently. Where existing callers provide only visitor ID, define/document deterministic fallback; allow native authenticated callers to identify their own project-scoped device. Validate device/visitor/project ownership before use.
- MMDB should be read once and shared for fast lookup; use a real deterministic, redistributable test database fixture, never an unstable live public-IP expectation. Country ISO and city strings should retain the empty-string contract for no match. Required mode fails startup on missing/corrupt DB; optional mode emits a visible degraded status and warning, not fake location.
- **Distribution:** prefer a deployment-owned updater and read-only mounted artifact over every request/task downloading from MaxMind. A scheduled updater validates the download, computes a checksum, publishes a versioned MMDB+manifest to selected private S3/MinIO or GCS storage; deployment materializes and verifies it before process start. Local Compose can use a shared file volume. Controlled rolling restart loads the new version; hot reload is not needed for the initial solo release. Keep MaxMind license credentials with the updater, not in events/logs. Document stale-copy fallback and maximum accepted database age as explicit deployment policy.
- Schema: no new warehouse-wide typed columns or historical-overlay table required for fresh launch. Existing properties can store canonical fields and a small internal enrichment version/provenance object, e.g. schema version + MMDB checksum + UA parser version. Extend internal-property exclusion so provenance is not accidentally exposed as user attribute/filter data. If provenance must be independently queried, use an additive nullable `enrichment_version`/JSON metadata column, but decide once before implementation rather than creating duplicate stores.
- Tests assert bytes/fields queued to each provider match the stored snapshot, not just a helper return. Fixture includes IPv4/IPv6, known/missing country/city, trusted forwarded IP, spoofed forwarded header, invalid/private/no IP, corrupt/missing MMDB, UA versions, screen fallback, new device context, and replay after alias/MMDB change.
- **Future replay/backfill semantics:** native outbox delivery always reuses persisted enriched facts. A future historical correction must be a separate operator-requested, versioned/reconcilable operation with stable event IDs and explicit chosen database/parser version. Current device/profile state is not evidence of historical event context. Where original IP/UA was not retained, leave unknown values rather than fabricate precise geography. No historical correction engine is needed before this fresh release.

## AN3 design: shared own/referral scopes, independent fixtures

- Build a shared canonical scoped-query layer with `own` and `referral/inviter` modes. Referral mode groups event-time `_attribution.link_visitor_id`, resolved through aliases; it must not filter on the invitee ID when user selects an inviter. Pair it with the signed purchase ledger inviter attribution, including reversals/refunds.
- Scope population/platform exactly as the chosen retained contract: referral totals span invitee platforms while an inviter-platform filter applies to the inviter's device. Record any deliberate simplification as a policy choice, not a passed parity test.
- Implement explicit keyset pagination (metric + stable visitor UUID tie-break) with cursor bound to scope/project/date/filter/sort; bounded page size, counts where the UI requires them. Whitelist metric and identity sort keys. Identifier search must search identity, not event name. Preserve zero rows for appropriate visitor detail behavior.
- Hydrate the metric page with visitor identity/summary and ledger revenue; detail adds own/referral metrics, generated-link count and effective metrics-since date. Reuse query primitives in server SDK/automation where their contracts align.
- Schema: likely query/index additions only. Explain query plans using representative data before adding speculative indexes. No daily aggregate subsystem needed. Signed purchase amount/ownership schemas already exist.
- Golden fixture: A invites B+C, B has own unrelated link, A also has own activity, a merged inviter alias, deleted/edited referral link, cross-platform devices, BUY+refund, empty/no-activity visitor, tenant D, >200 rows and equal-sort-value ties. Verify routed own/referral list and detail, page union, stable order and exact money units independently of production SQL.

## AN4 design: avoid an unnecessary replicated identity system at first launch

**Recommended:** change the customer-facing basic `/projects/{id}/analytics` endpoint to query PG canonical facts, returning the same current envelope and all-event count semantics. It must not simply reuse a countable-user metric, which would change custom-only visitor totals. Keep warehouse adapter query methods for explicit provider acceptance/diagnostics, clearly documenting their raw immutable identity semantics.

- Existing aliases flatten under the merge lock; canonical querying gives immediate merged identity without editing historical events or outbox payloads. Replays cannot reintroduce a split. No new schema needed.
- Acceptance: A+B events published, more A events queued, merge A→B, repeated delivery, chained merge B→C, concurrent ingest/merge, then compare basic/rich canonical identity counts under both ClickHouse and BigQuery configs. Exact event totals must remain unchanged; customer results must not depend on which delivery completed first.
- Add this interpretation explicitly to closure evidence. The audited A6 is divergence through a mounted customer endpoint. Direct ad-hoc warehouse queries over raw UUIDs are not automatically canonical and should not be advertised as such.

**Only if warehouse-direct canonical-identity SQL is required for initial launch:** add roughly **5–8d** and separate PRs for a versioned alias stream and each provider's canonical view. Each merge transaction emits durable alias updates for the full affected alias closure, with a monotonically increasing project revision; raw event IDs/payloads stay immutable. CH uses latest-revision identity rows; BQ uses a latest-revision view over append-only updates. Duplicate/reordered/retried updates must converge. Alias rows outlive event retention; project tombstones clean both identity and event tables and reconcile delayed exports. Pub/Sub acknowledgement is not view application: release cannot claim synchronous warehouse consistency without a completeness/watermark check or canonical PG fallback. Do not partially implement alias publication and call that consistent. This extension is unnecessary if the first-launch contract is canonical customer APIs plus raw warehouse export.

## AN5–AN7 design and acceptance

- Link export: reuse the canonical report counters for views/open/install/reinstall/reactivation/time-spent; retain available metadata/campaign name and established units. Do not claim to restore a real Rails CSV average engagement calculation: its old value is hardcoded zero. If improving that column, specify independently as enhancement. Snapshot job parameters and use bounded deterministic pages; existing lease, retry, escaping and authorization behavior remains.
- Usage: activity export reads retained canonical countable events and counts distinct canonical visitors in the exact requested daily/partial-month intervals; zero-fill periods. It does not substitute full-month billing snapshots. Keep a separately named billing-MAU export if needed because those snapshots intentionally survive event retention. Reject requests outside available activity retention instead of returning misleading zeros; this boundary is especially clear on a fresh installation. Tests use September1 vs September18 activity and a September15–20 request, plus month boundaries, merge, empty days, timezone contract and tenant isolation.
- Negative-cache pruning: durable periodic maintenance, bounded batches, predicate on current status/cached_until and seven-day grace. Conditional DELETE/row-locking must survive concurrent refresh without removing its new resolved row. Tests cover resolved, new negative, stale negative/transient and concurrent resolution; expose count/error in existing worker health.
- BQ IAM: add a narrowly scoped table-data deletion permission for the actual runtime principal, retaining separate Pub/Sub writer identity. Review Terraform plan and deletion protection; no permission to drop datasets is necessary for row DELETE. Mock contract tests remain useful but closure requires runtime-principal actual publish → arrival → project-scoped DELETE → verify other tenant remains. Test retry/local preservation when deletion is denied; restore permission and observe completion. Verify official Google IAM permission documentation during implementation.

## M1 deferred legacy conversion/archive import

M1 is **not a blocker for the fresh first release** and should not consume the initial 15–23d estimate. Keep an explicit deferred workstream; native `migrate` must continue to be described as native schema migration, not legacy conversion. Native encrypted-key restoration, DB/object restore, outbox recovery and project isolation are initial-release gates even though M1 is deferred.

When an existing Rails deployment is actually scheduled, plan M1 as several reviewable packages, not one giant importer:

1. **Inventory and contract freeze (S/M, 2–4d discovery):** actual Rails schema/warehouse/archive versions and sizes, secrets/attachments, source snapshots, write-freeze or CDC choice, supported historical range, semantic fixtures. Refine subsequent estimates from real inventory.
2. **Stable identity map + native entity conversion (M, provisional 4–7d):** persisted `(source deployment, table, legacy ID) → native UUID`, reusable across retries; users/instances/projects/devices/visitors/links/campaigns and dependency order; required source fields and explicit quarantine/report for invalid rows; unique source keys prevent collisions. Map credentials/keys under a planned rotation or compatible protected mechanism; never invent user ownership.
3. **Ledger/history/archive replay (M, provisional 4–7d):** integer/UUID mapping, event-time enrichment from original evidence, signed purchases and referral/identity state; gzipped archive streaming with file checksum + manifest + row checkpoint, bounded batches, stable event UUIDs, dry-run and idempotent restart. Frozen event identity must deduplicate overlap among Rails PG, old warehouse and archive sources; timestamp alone is not an event key.
4. **Reconciliation and rehearsed cutover (M, provisional 3–5d):** per-tenant/entity counts, foreign-key/orphan checks, counts by day/type, first/last identity, balances/refunds/subscriptions, metadata/object links, two interrupted replays, duplicate sources, quarantine acceptance, source-to-native read comparison and a proven rollback/restore. Emit redacted manifest/reconciliation artifacts tied to source hash and native image.

Provisional M1 implementation effort is approximately 13–23d after scope discovery; not a commitment, and actual dirty/large legacy datasets can materially expand it. It starts only when that separate deployment is authorized.
