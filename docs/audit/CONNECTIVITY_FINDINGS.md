# Connectivity, public links, SDK, domains, imports, metadata, automation and MCP audit

Read-only source audit, 2026-09-20. No tests executed and no cloud mutations. Rails implementation is the reference; parity documents and route-count matches are not proof. Paths are repository-relative; file line numbers refer to the source snapshot in SOURCE_SHA256.json. Findings below are implementation conclusions, not runtime-verified reproduction results.

## Confirmed missing or materially partial capabilities

### C1 — SDK blocks supported migration input shapes before invoking its implemented resolver (high)

- Rails: `app/controllers/api/v1/sdk/links_controller.rb:10-14` resolves native links then calls migration fallback; `:50-56` explicitly passes raw SDK URL/referrer. `app/services/migration_resolver.rb:54-78` dispatches HTTP(S), Play Install Referrer, and project-scoped bare/custom-scheme slug; `:83-111` implements Branch `~referring_link` and project-source lookup.
- Rust: `src/imports.rs:509-562` actually implements the corresponding helper, including referrer at `:531-546` and slug at `:548-561`. But `src/sdk.rs:570-574` first requires `url::Url::parse(raw)` to succeed; only afterward does `:586-603` call that helper for a parsed foreign host. The route wrapper makes the referrer and bare-slug branches unreachable from the SDK. `:588` also requires a URL host.
- Reproduction/scenario: establish an authenticated native visitor plus Branch source/cached imported link, then POST `/api/v1/sdk/data_for_device_and_url` with `visitor_id` and `url="~referring_link=https%3A%2F%2Fold.example%2Foffer"`, or `url="offer"`. Native returns invalid link URL instead of resolving imported deferred-link data. This is particularly relevant to Android Play Install Referrer. A syntactically valid custom-scheme URL with host can still reach the helper; do not claim all custom schemes fail.
- Tests: `tests/imports.rs:167` checks cached imports/project scoping and `:232` exercises Firebase/server SDK/public preview; `tests/sdk.rs:122` checks foreign/unsafe URLs. Searches of tests find no routed referrer or bare-slug success case. Testing `imports::resolve_sdk` alone would not catch this integration defect.

### C2 — MCP search tools silently route to simple lists, losing search/filter/statistics semantics (high)

- Rails: `app/controllers/api/v1/mcp/links_controller.rb:113-121` calls `LinkStatisticsQuery` with request params and campaign; `app/services/link_statistics_query.rb:238-257` applies campaign/sdk/active/id/ads/term filters, `:260-268` sorting, `:271-286` metrics. `app/controllers/api/v1/mcp/campaigns_controller.rb:19-35` calls `CampaignStatisticsQuery` and returns pagination metadata.
- Rust: `src/mcp.rs:830-834` maps both MCP searches to GET `/api/v1/projects/{p}/links` or `/campaigns`. `:899-910` serializes args as query params, but `src/core_api.rs:514-539` only accepts limit/offset and always returns active links ordered newest first. `src/core_api.rs:368-371` campaigns accepts no query at all and returns up to 1000 active rows. The actual rich native handlers already exist at `src/management.rs:89-123`; MCP does not delegate to them. JSON-RPC search tools use these same paths (`src/mcp.rs:930-938`).
- Reproduction/scenario: create two differently named links/campaigns, call MCP `search_links` / `search_campaigns` with a term matching only one; both simple list rows return. `active=false`, campaign filter, metric sort, Rails `page/per_page`, date/platform metrics are similarly not implemented by those targets. Native link limit/offset does work; do not describe pagination as wholly absent.
- Tests: `tests/mcp.rs:218` calls `search_links` without filters in OAuth/scope coverage. Rich search tests exist in `tests/management.rs:9` but exercise management directly, so can pass despite the MCP delegation error.
- Correction to preliminary note: MCP link analytics **does** honor `path` through `analytics_api::Range::new` resolving path to link ID. Do not report that as a gap.

### C3 — Uploaded image attachments are absent from link and domain-branding workflows (medium)

- Rails public quick link: `app/controllers/public/public_link_controller.rb:34-35` attaches the uploaded image; `:94-95` permits `image`.
- Rails SDK: `app/controllers/api/v1/sdk/links_controller.rb:37-43` passes `image` and `image_url`; `app/helpers/sdk_link_builder.rb:31-32` attaches bytes.
- Rails dashboard link create/update: `app/services/link_management_service.rb:7-25` accepts/attaches image; `:35-47` swaps/purges attachments; `:125-126` helper attaches. Domain branding: `app/controllers/api/v1/domains_controller.rb:69` passes `generic_image`; `app/services/domain_configuration_service.rb:15-23` attaches uploaded image, clears competing URL, or switches to URL and purges attachment.
- Rust quick link: `src/public_links.rs:633-639` accepts only JSON (32 KiB); `:666-679` validates external image URL and saves metadata. Rust SDK link: `src/automation.rs:220-225` extracts JSON; `:101-105,208-214` saves JSON metadata, with no storage/attachment operation. Dashboard create/update are JSON (`src/core_api.rs:496-509,557-562`), image/og-image URL metadata handling at `:1319-1323,1366-1369`. Domain branding `src/domains.rs:747-751,783-790` handles only `generic_image_url`. Rendering only reads URL values (`src/public_links.rs:515-519`, quick link `:620`), not image object keys.
- Reproduction/scenario: upload image multipart to any corresponding native JSON handler: rejected by JSON extraction/parser. Passing a JSON `image` or `generic_image` does not attach or render it. External `image_url` continues to work. Existing uploaded Rails thumbnails/brand art need an explicit conversion/publishing path at cutover.
- Generic native object storage is not an equivalent image feature: `src/integrations.rs:69-105` requires dashboard authorization, lacks image binding/ownership lifecycle, and downloads as `application/octet-stream` plus `Content-Disposition: attachment`; anonymous preview crawlers cannot use it as an image attachment URL. The new GCS/MinIO option does not by itself restore these attachment workflows.
- Test coverage: repository-wide search for multipart/generic_image upload test paths found none; image assertions cover URL/default metadata, not attach/replace/purge and anonymous rendering. `tests/providers.rs` generic storage byte tests therefore cannot establish Rails attachment parity.
- Scope distinction: native app-store artwork caching is implemented in `src/app_metadata.rs` (downloaded bytes and public artwork route); this is not missing. Platform push certificates/API-key blob uploads are separate credential-administration contracts, not image attachments; Rails attachment evidence is `app/services/platform_configuration_service.rb:46-62,85-98,121-134`. Native messaging profile/environment administration is covered in ENTERPRISE_FINDINGS.md (E9).

### C4 — Clipboard status no longer supports the tokenless project-activity check (medium)

- Rails: `app/controllers/api/v1/sdk/links_controller.rb:33-35` returns `clipboard_active` with no clipboard token. `app/services/clipboard_activity_service.rb:3-12` stamps/reads a project TTL marker. `app/services/platform_render_decision_service.rb:45-49` stamps it when a preview configured to copy the clipboard is opened.
- Rust: `src/sdk.rs:743-751` requires `clipboard_token` then checks a matching unhandled click within 48 hours and returns `available`. No tokenless aggregate/project activity signal exists in this handler.
- Scenario: SDK asks whether recent project activity justifies attempting a clipboard read before the read/privacy prompt. Rails can answer; native `{}` request returns `clipboard_token required`. Caller now must read clipboard first to ask status. Merely renaming response keys cannot restore this behavior.
- Tests: `tests/sdk.rs:63-118`, especially `:86-87`, exercise status using the already-known click token; they do not test the tokenless activity TTL protocol. Native token validation/consumption is implemented and is a different useful capability.

### C5 — Declared SDK app/platform configuration restrictions are optional and can be skipped (medium; same-project policy gap)

- Rails: `app/controllers/api/v1/sdk/base_controller.rb:12-16` requires project-key/platform/identifier; `:25-35` requires configured application+redirect configuration; `:37-49` validates Android package, iOS bundle, linked web domain.
- Rust: `src/auth.rs:169-182` authenticates project key, but `:183-194` makes platform/identifier/origin optional and enters configuration checks only if platform or Origin is present. Omitting both skips `enabled=false`, app identifier, and web-domain restrictions. Even with platform supplied, missing config is `{}` (`:195-201`) and only explicit `enabled=false` or existing expected identifier is enforced (`:210-219`).
- Scenario: disable project iOS SDK configuration, then make a native SDK call with valid project key and no platform/origin declaration; extractor permits it. Supplying iOS platform would deny it. This is not evidence of cross-project access and declared app identifiers are not cryptographic app attestation; describe only the lost mandatory configuration gate.
- Tests: `tests/sdk.rs:274-337` tests wrong/absent identifier with declared platform and allowed/disallowed Origin, but never the all-omitted header tuple; `:353` onward tests declared iOS binding. Existing tests can pass while callers skip the policy.

## Confirmed behavioral edge that needs product decision before calling a missing capability

Migration/domain setup compensation changed. Rails provisioning destroys a new DB row when Cloudflare create+lookup fail (`app/services/custom_domain_provisioning_service.rb:48-59`); migration setup compensates downstream failure with hostname teardown (`app/controllers/api/v1/migrations_controller.rb:81-110`). Native `src/imports.rs:657-667` commits source/hosts, then on provisioning failure deletes only source. `src/domains.rs:404-410` has already inserted custom_hostname and deliberately retains it for durable provisioning retry. Result: failed migration-create can leave a claimed migration-purpose hostname without a source, and lifecycle can later provision it. This is source-proven partial state, but native durable recovery may be deliberate; report as a lifecycle contract/recovery question, not an unqualified permanent wedge. Combined migration-create + Cloudflare failure rollback/retry test is absent; Cloudflare mock test `tests/domains.rs:87` tests provider adoption/deletion directly, not this controller combination.

## Route/wire compatibility distinctions (not automatically missing capabilities)

- SDK authentication/identity moved to hashed project API keys and native visitor UUIDs; Rails had project identifier plus LINKSQUARED hash/device lookup (`app/controllers/api/v1/sdk/base_controller.rb:8-10,55-74`; `src/auth.rs:169-182`; `src/sdk.rs` visitor_id/canonical/authenticate). Existing SDK clients need adaptation; native identity/authenticate/merge are present.
- Rails POST SDK `link_details` serializes link (`app/controllers/api/v1/sdk/links_controller.rb:23-30`); native exposes GET `/api/v1/sdk/links/{path}` (`src/core_api.rs:914`). Native capability exists even if old path absent.
- Native SDK resolver routes are `/api/v1/sdk/data_for_device`, `/data_for_device_and_url`, `/data_for_device_and_path` (`src/sdk.rs:799-801`), with native visitor/body contract. Route name differences alone should not count as missing fingerprint/URL/path resolution.
- Native domains/configuration and MCP delegate response shapes differ from Rails serializers; root route inventory is navigation only. Matched route strings do not prove working body contract or behavior (C1/C2 illustrate this).
